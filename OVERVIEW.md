session-recovery tracks running Paseo turns and continues unfinished sessions after the daemon restarts. A Goal pill beside Tasks and Subagents above the composer lets you toggle continuation for the current goal after a normal turn ends. It appears only for supported goals, and hides when the goal is complete or cleared. The recovery screen also has a toggle for goal sessions. Only selected goals are continued. A new objective needs a new selection. It starts tracking with the next observed turn; an existing session can be selected from the Command Center.

![Recovery and goal settings](assets/goal-settings.png)

Automatic recovery is on by default for main sessions, with a 60-second delay, up to three attempts per interruption, and a 24-hour recovery window. The delay doubles after each attempt, up to 15 minutes. Subagent recovery and retries for recognized temporary provider errors can be enabled separately.

The recovery screen shows scheduled continuations, goal states, sessions that need review, exclusions, and recent activity. You can preview a continuation before sending it manually, dismiss a candidate, or exclude a session from future recovery. Direct stops, questions, and approvals are excluded from automatic recovery. Uncertain delivery requires checking the conversation.

Goal continuation is off by default. Enable Continue selected goals in settings, then use each session's toggle to choose its current goal. The default delay is 60 seconds, with 10 continuations per objective. Turning a session toggle off cancels pending goal continuation and keeps interruption recovery available. Existing goals start unselected on upgrade. Codex uses its official goal lookup API through a local subprocess running the configured provider command. The subprocess only initializes and reads goal state. OMP and compatible Pi goal tools use structured conversation results; OMP goal update events are included. A provider must expose a supported goal state. Paused, blocked, complete, cleared, limited, and unknown goals do not continue automatically. The plugin cannot verify that a goal marked complete was actually achieved.

OpenCode support uses the Goal agent mode from opencode-goal-plugin and reads the focused objective from its version 1 per-session state file. Set an objective with /goal before selecting it. Other modes and queued goals are excluded. The Paseo toggle controls fallback messages, not OpenCode's own goal loop; use /goal pause to pause that loop. Native continuation claims, child-session guards, pauses, blockers, and limits are respected. Native resume commands and budget resets are never sent automatically. The default project-local state path and OPENCODE_GOAL_STATE_PATH in the provider environment are supported, including custom providers extending OpenCode. Missing, changing, malformed, or outdated state requires review. Legacy global state and JavaScript-only state path overrides are not discovered.

Recovery starts a new turn in the existing conversation using its current provider and settings. The message asks the agent to check existing work before repeating commands or external actions. It cannot restore an interrupted process. Lifecycle events are best effort, so an interruption cannot always be classified. Paseo 0.11 and 0.12 have no atomic send-if-idle request; the plugin rechecks before submission, but a concurrent action can still race it.

Requires a macOS or Linux daemon running stable Paseo 0.11.4 through 0.12.x and a provider with saved history. Background workspaces are included on 0.12. Only Paseo-managed sessions are covered. The paired session-janitor 0.1.2+ protects pending recovery and goal continuation from cleanup; other cleaners do not read those protections. Composer visibility checks and goal mode read supported goal state and conversation records in memory. Visibility checks run even with automatic continuation off and do not select or resume sessions. Only fingerprints, selection, state, and continuation count are stored alongside session metadata. Local files use owner-only permissions. Continuations use the existing session and provider, with normal provider usage and billing.
