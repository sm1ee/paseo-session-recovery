session-recovery tracks running Paseo turns and continues unfinished sessions after the daemon restarts. Press Goal · On / Off beside Tasks and Subagents above the composer to toggle continuation for the current goal directly. When continuation is held, the button shows Blocked, Paused, Waiting, Limit, or Review. It appears only for supported goals, and hides when the goal is complete or cleared. Goal details and settings are on the recovery screen. Only selected goals are continued. A new objective needs a new selection. It starts tracking with the next observed turn; an existing session can be selected from the Command Center.

The sidebar shortcut appears on desktop and web. In the iOS and Android apps, open the screen from the Command Center. Per-session Goal toggles are available on all clients.

For a native Codex, OpenCode Goal-mode, or Claude Code session, enter /goal or /goal edit to view and edit the prefilled current objective. /goal-edit and View or edit this session's goal in the Command Center open the same editor on desktop and mobile. It reads only the requested session when opened or reloaded. Completed goals, exhausted limits, pending approvals, and uncertain delivery are read-only. An edited objective needs a new continuation selection. Other providers retain their native /goal behavior.

Codex uses Save goal, or Save and activate for paused/blocked goals; its native command preserves the token budget and usage. OpenCode uses native /goal edit and preserves the focused goal ID, turn/token/time budgets, usage, and history. Paused/blocked goals become active. OpenCode requires opencode-goal-plugin's registered Goal mode, native /goal command, and version 1 session state. Its command and agent must reference a valid configured model. Both native goal loops can start work after saving.

Claude uses Replace goal and start: its native /goal command replaces the condition, immediately starts a turn, and resets the goal timer, evaluated turn count, and token-spend baseline. It does not expose a separate goal token budget. Reported tokens are from the last native evaluation. Claude's native command must be allowed by workspace trust and hook policy. OpenCode and Claude edits wait until the session is idle and accept up to 4,000 characters. OMP's current goal RPC has no objective-update operation, so its editor remains unavailable.

Claude goal reads follow native goal_status records on the current transcript's parent chain, bounded to the last 8 MiB. Missing, changing, incomplete, or unrecognized records require review. CLAUDE_CONFIG_DIR in the inherited provider environment is supported. Wrappers or hooks that change the directory must expose the same path there. Background composer discovery does not scan Claude transcripts; use the editor or Command Center for an existing Claude goal. Claude's native goal loop owns continuation, and the plugin does not send an extra fallback while that goal is active.

Automatic recovery is on by default for main sessions, with a 60-second delay, up to three attempts per interruption, and a 24-hour recovery window. The delay doubles after each attempt, up to 15 minutes. Subagent recovery and retries for recognized temporary provider errors can be enabled separately.

The recovery screen shows scheduled continuations, goal states, sessions that need review, exclusions, and recent activity. You can preview a continuation before sending it manually, dismiss a candidate, or exclude a session from future recovery. Direct stops, questions, and approvals are excluded from automatic recovery. Uncertain delivery requires checking the conversation.

Goal can be enabled during a running Codex turn. Its native resume command changes goal state without stopping that turn. When idle, Codex may start its own goal turn immediately. The plugin follows that turn and waits for completion and the configured delay before sending a fallback continuation. Paseo must expose its native /goal command for that session. Custom Codex launch wrappers need to support --version; after correcting a wrapper, reload affected sessions when idle.

Goal continuation is off by default. Enable Continue selected goals in settings, then use each session's toggle to choose its current goal. The default delay is 60 seconds, with 10 continuations per objective. Turning a session toggle off cancels pending goal continuation and keeps interruption recovery available. Existing goals start unselected on upgrade. Codex uses its official goal lookup API through a local subprocess running the configured provider command. Background checks only read state. Explicitly turning the toggle on can also resume a blocked Codex goal using its goal API, preserving its objective, token budget, usage, and continuation count. Previously selected blocked goals need one off/on cycle. Input requests, direct stops, and exhausted limits still prevent resumption. The subprocess never loads a thread or starts a turn. OMP and compatible Pi goal tools use structured conversation results; OMP goal update events are included. A provider must expose a supported goal state. Paused, blocked, complete, cleared, limited, and unknown goals do not continue automatically. Selected inactive goals are rechecked in case their native state becomes active. The plugin cannot verify that a goal marked complete was actually achieved.

OpenCode support uses the Goal agent mode from opencode-goal-plugin and reads the focused objective from its version 1 per-session state file. Set an objective with /goal before selecting it. Other modes and queued goals are excluded. The Paseo toggle controls fallback messages, not OpenCode's own goal loop; use /goal pause to pause that loop. Native continuation claims, child-session guards, pauses, blockers, and limits are respected. Native resume commands and budget resets are never sent automatically. The default project-local state path and OPENCODE_GOAL_STATE_PATH in the provider environment are supported, including custom providers extending OpenCode. Missing, changing, malformed, or outdated state requires review. Legacy global state and JavaScript-only state path overrides are not discovered.

Recovery starts a new turn in the existing conversation using its current provider and settings. The message asks the agent to check existing work before repeating commands or external actions. It cannot restore an interrupted process. Lifecycle events are best effort, so an interruption cannot always be classified. Paseo 0.11 and 0.12 have no atomic send-if-idle request; the plugin rechecks before submission, but a concurrent action can still race it.

Requires a macOS or Linux daemon running stable Paseo 0.11.4 through 0.12.x and a provider with saved history. Background workspaces are included on 0.12. Only Paseo-managed sessions are covered. The paired session-janitor 0.1.2+ protects pending recovery and goal continuation from cleanup; other cleaners do not read those protections. Composer visibility checks read session metadata and native Codex or OpenCode goal state without restoring conversations. For OMP and other goals exposed through conversation records, select an existing goal from the Command Center. Selected goals retain their checks before automatic continuation; their toggle can show the last checked state without loading history. Background requests for the same session share a result. Sessions without a visible goal are checked again after five minutes or a relevant session change. Each client runs up to four checks at a time. Display checks run even with automatic continuation off and do not select or resume sessions. Only fingerprints, selection, state, and continuation count are stored alongside session metadata. Local files use owner-only permissions. Continuations use the existing session and provider, with normal provider usage and billing.
